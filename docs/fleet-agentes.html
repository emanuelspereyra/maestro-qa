Maestro QA — cómo se reparte el trabajo

Fleet de Agentes

Un ticket entra una sola vez. El orquestador decide, por lo que el ticket dice, cuáles de los 12 agentes especializados corren — nunca los 12 a la vez — y encadena el resultado de unos como insumo de otros antes de llegar a un veredicto final.

01 Cómo se distribuye la carga

No hay un router por LLM decidiendo qué agente conviene — sería más lento y menos predecible. La clasificación es por palabras clave del texto del ticket (classify_agents), determinística y gratis. Dos agentes corren siempre; el resto se prende solo si el ticket lo amerita.

02 Los 12 agentes

Agrupados por cuándo entran en juego, no por orden alfabético.

Base — corren siempre, sin importar el ticket

casos_manuales siempre · 1º Casos de prueba manuales estructurados. Su salida se inyecta en todos los demás.
trazabilidad siempre Cruza criterios de aceptación contra los casos generados — qué quedó cubierto, qué es un hueco.

Especialistas — por palabra clave del ticket

automatizacion automatiz, e2e, ci/cd Page Object + test Playwright (frontend). Puede explorar/editar el repo real si está conectado.
automatizacion_api endpoint, api rest, backend Cliente HTTPX + test pytest (backend).
datos_prueba datos de prueba, dataset, carga masiva Dataset generado por seed — mismo seed, mismos datos.
performance performance, prueba de carga, latencia Locustfile listo para correr.
priorizacion_bugs bug, defecto, incidencia, hotfix Borrador de defecto. Severidad técnica sí; prioridad de negocio siempre queda "pendiente de decisión de negocio".
seguridad seguridad, vulnerabilidad, owasp Casos tipo OWASP + hallazgos de SonarQube si está conectado.
documentacion documentar, manual de usuario Changelog / guía de usuario / referencia técnica según lo que pida el ticket.
regresion regresión, suite completa Qué áreas ya cubiertas hay que re-verificar por este cambio.
bug_explorer causa raíz, root cause, por qué falla Causa probable de un bug — archivo:línea real si hay repo conectado, hipótesis conceptual si no. Nunca inventa un path.

Revisión y cierre

calidad_codigo revisar código, code review, refactor Sobre-ingeniería / AI-slop en código real. Solo lectura — nunca escribe, ni con acceso a repo.
release_readiness siempre · último Lee el resultado de todos los demás y da veredicto: GO / GO_WITH_CONDITIONS / NO_GO.

03 Cómo se derivan las tareas entre agentes

Ningún agente reinterpreta el ticket desde cero — el orquestador le agrega al intake de ciertos agentes lo que otro ya produjo en la misma corrida, como contexto extra al final del mensaje.

casos_manuales → todo el resto

Sus casos (con data_contract, steps, business_rule_ids) se agregan como "Casos de prueba ya generados" al mensaje de cada especialista que corre en la misma tanda — así automatizacion automatiza los pasos reales, no una versión inventada del ticket.

automatizacion(_api) → calidad_codigo

El Page Object/test o cliente API/test recién generado se agrega como "Código generado en este run" — por eso calidad_codigo corre al final de los agentes "normales": necesita ver ese código para poder auditarlo.

04 Qué pasa si algo falla

  • 01 Cada agente corre aislado — si uno tira una excepción, se marca (error) y el resto de la tanda sigue sin verse afectado.
  • 02 release_readiness recibe un encabezado determinístico ("Agentes con error: …") — si hubo errores, corrige el veredicto a NO_GO aunque el texto libre del LLM diga GO.
  • 03 Las integraciones externas (repo real, push+PR, Azure DevOps) nunca rompen la corrida: si fallan, el resultado ya generado se devuelve igual, con el motivo en "Pendiente".
